# Key Learnings
Dense memory bank for surprising lessons learned by trying things. Keep this under 200 lines by recompressing it. Raw chronology belongs in `agent_notes/loose_notes/`.
- Gauged UVT Trace Atlas is the current mathematical target for complex known-camera paths: treat STAR UVT tensors as one local chart of a camera-ray bundle `pi: E_Gamma -> B`, `B=Omega x T`, with trace `pi_* Gamma^* world_primitive`; revolving cameras should be projective/rational/gauged atlases with visibility strata, not one affine UVT tube plus fallback. Current gates include projective atlas-cell Metal forward, direct VJP through homogeneous/cell coefficients, coefficient-only loss-decrease smokes, and a frame-scaling probe where interval atlas entries stay `13 -> 13` over `4 -> 64` frames while dense project/bin pairs grow `35 -> 555`; one-parameter camera-family math now extends the base to `Q x Omega x T`, proves value/primitive/q-gradient gauge invariance, and shows one QxT metadata chart stays constant while per-q replay grows `16x` with final payload ratio `0.106` and `0.306px` max UV fit residual; two-parameter camera-family shared-work now extends that to `Q2 x Omega x T`, where one chart stays constant while per-q-pair replay grows `64x`, final payload ratio is `0.0625`, final chart ratio is `0.015625`, and max UV fit residual is `0.111px`. `ProjectiveCellIntervalTrainerState` detects optimizer-moved support/depth-order flips, rebins metadata without replacing the live coeff tensor, compiles support tile-boundary roots into time-local tile runs, compiles depth-order crossings into stable event-root/time-run strata before fallback, isolates exact root samples so fallback is local, and turns finite-exposure/rolling schedules into sample-indexed interval atlases; rolling batches unique sample times with `row_weights[Q,H]`, uses a row-weighted interval Metal kernel that skips zero-weight sample/row pairs, and `fallback_render_mode=mixed` patches fallback regions with differentiable live-depth reference while fast regions keep interval Metal VJP. The production feature trainer rejects `projective_interval.enabled` unless a `ProjectiveTraceCellTraceAtlas` producer is explicit; the first compatible STAR UVT producer now completes the spatial quadratic, lowers exact isotropic affine tubes into atlas rows, and carries temporal opacity as `opacity_time_coeffs` through reference, interval Metal forward/rows, and direct VJP. Support churn on the current cap128 smoke is mostly subpixel boundary noise: trace-budgeted is cap-safe but rebins `7/7`; overshoot telemetry shows max `0.0912px`, and `support_stale_overshoot_epsilon=0.5` recovers `0/7` rebins, identical `0.0847767964` loss, zero overflow, and `1277.5ms` measured no-first. `slack_budgeted` is now the first support-event-distance allocator, spending crowded guarded-tile slots on traces nearest to the tile boundary instead of primitive id order. Image-level debounce tests show why certificates matter: with real support padding, `0.05px` overshoot stays under `1e-4` max RGB error, a tiny orbit-derived rational trace with `~0.056px` overshoot also stays under `1e-4`, but center-only support with the same overshoot exceeds `0.35`; `support_stale_tail_alpha_epsilon` now aggregates omitted alpha per missing sample/tile, so overlapping low-alpha support loss cannot be hidden by a per-trace max. Paired/combined orbit visibility tests confirm support debounce does not suppress stale order repair, the orbit depth-root test proves continuous projective visibility roots split one orbit cell into stable order strata without fallback, and the first combined orbit stress exercises tail-alpha support reuse + visibility-root stratification + slack-budgeted guard allocation in one refresh. Real high-motion trainer support now has a compact matrix: default measured support rebins 9, guarded slack-budgeted support rebins/stale refreshes 0/0 over guard 0.25/0.5/1/2, max guarded no-first ratio `0.590`, max rebuild ratio `0.5`; a source-distinct real-video trainer matrix adds 3 checked-in segments/6 rows with exact cadence-loss match, max no-first ratio `0.550`, rebuild ratio `0.5`, and zero support rebins/stale refreshes/fallback/overflow/visibility stratifications; the source-distinct frame-scaling matrix extends those 3 segments over `4/8/16` frames with 18 rows, frame-growth `4x`, max no-first ratio `0.690`, no-first/frame-growth ratio `0.438`, rebuild growth `1.0`, rebuild ratio `0.5`, and zero support churn; the quality tether adds 9 saved cadence/measured case pairs with exact loss-curve/RGB-loss/end-PSNR agreement, min PSNR gain `0.0223`, and all gradient flags; the media tether adds actual contact-sheet writer agreement on 3 source-distinct pairs with pixel delta `0`, matching PNG hashes, final RGB loss delta `0`, max loss-curve delta `7.45e-09`, min PSNR gain `0.0451`; the goal audit proves 31 rows while keeping completion open. Treat these as bounded experimental mechanisms pending broader-scene image/error validation. Remaining producer gaps are anisotropic precision, pixel-varying depth, and WorldFoam/instance cells.
- MPS made the tiny TokenGS experiments usable but not automatically fast: external kernel/resource contention can dominate perceived speed, and lowering token count changes capacity, so decouple encoder input size from render/loss size when using smoke-test speed knobs.
- DUSt3R's second apparent pass is global alignment, not duplicate inference, and its extra lens metadata is noise until distortion/photometric modeling exists; logs should separate pair inference from alignment and preserve only the camera fields the renderer consumes.
- Stale extracted frame folders are dangerous UX even when the code loads explicit JSON records. Users look at folders, so extraction should clear or isolate outputs to avoid misleading evidence.
- Rendering without camera extrinsics lets the model cheat with frame-conditioned gaussians. For dynamic novel view synthesis, using `camera_to_world` in the renderer is not optional.
- DUSt3R per-frame focal estimates can jitter on a phone clip. Median focal across the sequence is often a better default than trusting each frame.
- A single shared `BaseTrainer` would hide real differences between known-camera, image-implicit, and video-token implicit training. Shared payload contracts are cleaner than shared trainer inheritance.
- Positional tuple outputs were fine for toy iteration but became risky as soon as camera state, videos, and multiple baselines appeared. Named runtime payloads are the right boundary.
- `SequenceData.__getitem__` was useful as a temporary migration crutch, but it hid weak contracts. After trainer call sites moved to attributes and `ClipBatch`, deleting the bridge made violations easy to grep.
- System `python3` can pass compile checks but fail import smokes because dependencies live in the `uv` environment; use `uv run python` for meaningful Dynaworld checks, and check script mode before assuming a wrapper can be run with `./...`.
- JSONC configs are better than environment-variable fanout for trainer experiments. Shell wrappers should choose config files rather than re-declaring every knob.
- Shared JSONC helpers belong in one tiny utility. Keeping `strip_jsonc_comments(...)`, config loading, and W&B-safe serialization in `src/train/config_utils.py` avoids both parser copy-paste and a mirrored Python default map.
- `render_size` should be treated as a viewport, not a crop. Scale `fx/fy/cx/cy` from encoder input pixels to render pixels at the render boundary, then resize GT for loss; pose and FoV stay unchanged.
- Keep full experiment defaults in JSONC, not in a mirrored Python `DEFAULT_CONFIG`. Python should normalize runtime values, validate required sections, and keep constructor-name mapping in one boundary factory.
- On the MPS prebaked-camera baseline, AMP/flash attention was slower because dense splat render/backward dominated. Batched dense rendering improved frame throughput more than reducing `frames_per_step`, which mainly improved iteration rate.
- Do not synthesize higher-FPS camera-bake videos from an already downsampled low-FPS clip. The duplicate/interpolated temporal signal can distort DUSt3R camera estimates; generate bake variants from the original source frames with the final crop/FPS/scale in one ffmpeg pass.
- DUSt3R pose scale is arbitrary enough to break fixed-volume Gaussian heads. The 128px/4fps bake produced camera z translation up to `2.56` while TokenGS initial z is constrained to `[0.5, 2.5]`, putting late-frame Gaussians behind the camera and causing render NaNs before any optimizer update.
- The committed stable prebaked-camera baseline was 32px/2fps/all-frames, not the new 128px/4fps camera trajectory. Treat 64/128 video-size bakes as new camera-distribution tests, not just higher-resolution versions of the same stable run.
- Camera/scene normalization is a pretraining contract, not just a local init tweak. Gaussian extent, camera radius, path residual scale, FoV, near plane, and Plucker moment scale all need a shared canonical frame or each DUSt3R solve can define a different task.
- Upstream `taichi-splatting==0.13.0` is not installable in the repo's Python 3.11 `uv` env, but the vendored fork now has a Taichi 1.7.4/Metal-compatible Torch autograd path. Treat the local fork as the source of truth for Mac renderer experiments, not the pip package.
- The copied `memory_efficient_sparse` rasterizer is not a good MPS benchmark default despite its name. Its per-splat Python-loop custom autograd path was hundreds of ms at 64px/128 splats and seconds at 64px/512 splats, while custom/vectorized sparse stayed around tens of ms after warmup.
- Benchmark summaries must account for skipped optional backends. Timing means over only `status == ok` silently hid Taichi/gsplat on MPS, making the renderer matrix look smaller than what actually ran.
- The checked-in trainers are still tiny for renderer scaling: the prebaked-camera defaults decode 128 tokens x 4 splats/token = 512 splats. A 64k-splat real-time target needs a separate forward-only throughput benchmark; dense `G*H*W` paths are not meaningful at that scale.
- Porting `taichi-splatting` to Mac is not a simple CUDA-shader swap. CUDA sort/cumsum can be replaced with Torch fallback, but the fast rasterizer also uses Taichi SIMT block/warp intrinsics unsupported by Metal. A Metal path needs separate forward/backward kernel structure; the current local patch is a simple global-memory reference path, not a tuned Metal renderer.
- Taichi/Metal benchmark timing needs an explicit Taichi sync at timing boundaries (`TaichiQueue.run_sync(ti.sync)`), not just `torch.mps.synchronize()`. Without that hook, mixed PyTorch/Taichi measurements are easy to mistrust even when the final numbers happen to stay similar after sync.
- The local Taichi/Metal backward path is not just "finite gradients": against a direct CPU-float64 Torch packed-2D raster reference, 16/32px cases with 4/8/16 splats matched forward and packed/features gradients at ~1e-8 absolute error. This validates the core simple Metal raster/backward math, separate from 3D projection correctness or performance.
- Taichi 1.7.4's public `parallel_sort` works on Taichi fields, not Torch tensors, and `PrefixSumExecutor` explicitly rejects Metal. A native Metal bin/sort path cannot just flip the current Torch fallback to Taichi algorithms; custom ndarray scan/sort kernels work on MPS but odd-even sort is far too slow (`128x128/G=65536` around 1.5s).
- A Metal-native ordered per-tile binning path that preserves input order is correct when splats are already depth-sorted, but the naive tile-major implementation is still slower than the Torch-sort reference (`128x128/G=65536` 68ms vs 31ms). The next real win needs a better algorithm, not merely “move sort to Metal.”
- A Taichi-only compact bucket sorter can do the right high-level GPU-binning shape on Metal and passes forward/backward accuracy, but it still loses to the Torch-sort reference (`1024x1024/G=65536` 125.6ms vs 52.1ms forward). Without a fused threadgroup-memory sort+raster kernel, Taichi spends too much time in separate bin/sort/raster stages.
- Low precision is not a simple cast in the Taichi path: the current tile mapper imports f32 `Gaussian2D` and expects f32 depths. fp16 needs separate mapper/raster kernels, not just `features.to(float16)`.
- MLX `mx.fast.metal_kernel(name=...)` requires a valid Metal/C identifier. The raw rasterizer's first cache-derived names contained `=`, `.`, and other config punctuation, causing Metal compile failure before any math ran.
- MLX `mx.eval(...)` is an in-place evaluator in the tested `mlx==0.31.1` path and returns `None`; evaluate first, then read `.item()` from the original array.
- Raw MLX/Metal and the Taichi accuracy reference sample pixels at `x + 0.5`, while the current Dynaworld dense/Torch sparse training renderers sample integer grid coordinates. Use the packed-2D accuracy benchmark for correctness; throughput comparisons against training renderers can show expected image diffs until sampling conventions are unified.
- Torch custom-op schemas declared as fixed tuple returns, e.g. `-> (Tensor, Tensor)`, must be implemented with fixed C++ tuple return types. Returning `std::vector<torch::Tensor>` registers as `Tensor[]` and aborts at extension import with a schema mismatch.
- Do not pass tightly packed Torch `[G,3]` float tensors to Metal kernels as `device float3*`. Metal `float3` has 16-byte alignment/stride while Torch rows are 12 bytes, so splats after index 0 read corrupted conics/colors; use flat `device float*` plus `index * 3` loads or an explicitly packed type.
- Random-splat sort pressure is not currently dominated by Taichi's OBB tile test: exact conic/tile intersection only reduced keys by ~8-10% at 64px/1024 and 128-1024px/64k. Same-tile custom rectangular bounds were ~1.29x exact keys in a 64px/512 probe, so future speed work should check `K/G` before assuming AccuTile will fix Taichi.
- In the Torch+Metal fastpath, saving sorted tile IDs fixed one real backward tax, but v3 still beat v2 while re-sorting in fast backward. That shifts the next optimization model toward parameter bandwidth and global atomic gradient pressure, especially under tile overlap.
- Porting saved sorted tile IDs into v3 confirmed the sort tax is still worth removing: it made forward ~1-2ms slower at 4K/64K because of writeback, but reduced estimated backward ~12-14% and forward+backward ~7-9% in no-overflow synthetic cases.
- Direct Torch projected splatting is only a small-scene baseline, not a 4K/64K comparator. At 128x128/512 it was already ~22-27x slower than v3 forward and ~73-93x slower forward+backward; 4K/64K would be ~1.1e12 pixel-splat evaluations.
- Passing MPS slice views like `packed[b]` through the single-image Taichi autograd function can trip PyTorch version-counter checks during backward. Native Taichi batch rendering avoids that train-loop hazard by keeping `[B, G, ...]` tensors intact through one autograd call.
- Small low-res/low-splat Mac raster benchmarks are launch/overhead dominated, so v2 can beat v3 there even though v3 wins large-scene backward. For bootstrap training at 64-128px with hundreds of splats, choose the low-overhead renderer first; switch to v3 when tile occupancy, wider splats, or 64k-scale gradients make bandwidth/recompute behavior dominate.
- Taichi batch speedup claims are baseline-sensitive. In a fresh `B=4, 128x128, G=128` run, Taichi absolute time was close to the README order of magnitude, but a looped MPS direct-Torch reference was far faster than the README's direct-Torch baseline, shrinking the speedup factor. Compare absolute ms and reference implementation, not just `x` speedups.
- At `1024x1024/G=65536`, Taichi/Metal remains useful as a compatibility path but its backward is not in the same class as pure Metal: measured forward+backward was about `352/1081 ms` for Taichi vs `41/120 ms` for v2 and `20/40 ms` for v3 on sigma `1-5/3-8`.
- The Mac renderer stack now has three distinct proven roles, not one winner: Taichi for compatibility/native batch, fast-mac v2 for tiny bootstrap overhead, fast-mac v3 for large/backward-heavy training. Future renderer selection should be scenario-based, not repo-brand based.
- "Warm" renderer timing means first-use compile/setup effects are excluded, not that rendered splats or outputs are cached. Reusing the same synthetic splats across warmup/timing is fine for kernel timing as long as command sync is correct and no one claims data-randomization coverage.
- Batch support is asymmetric: Taichi has real `[B,G,...]` native batch, while fast-mac v2/v3 are currently single-image APIs looped over frames. This makes Taichi more train-loop convenient than its raw raster speed suggests, and makes a native fast-mac batch API a high-leverage next step.
- fast-mac v5 validates that native `[B,G,...]` Torch+Metal batch support is real and improves forward per-frame throughput (~2x at 4K/B=4 synthetic), but it did not replace v3 for B=1 forward+backward; batching/eval split is an API and forward-throughput win, not automatically a backward win.
- fast-mac v6 showed an active-tile trap: if almost every tile is active, compacting/sorting active tiles and pre-filling the full `[B,H,W,3]` background can make forward ~3x slower. Exposing the existing direct tile kernels and making active scheduling opt-in restored v5-like forward while keeping faster B=4 backward.
- Raster benchmark case labels can lie if conic conventions differ. v5's standalone benchmark initially used `1/sigma` while v2/v3 used inverse variance `1/sigma^2`, changing splat footprint under the same `sigma 3-8` name.
- The raw MLX/Metal path was valuable as a proof of Metal raster viability, but bridge overhead and dependency split make direct Torch custom ops the better training path. Keep raw MLX in `shader_experiments` for provenance/experiments, not as the main renderer backend.
- Very low opacity is not a free stability win for Taichi training. In the 128px/8192-splat baseline, `opacity_init=0.02` stayed finite but slowed to ~1.1-1.3 it/s because rays did not saturate early; `opacity_init=0.1` was a better local default while still avoiding the old near-0.5 opacity saturation.
- A white fast-mac render is not necessarily a renderer/background bug. v5 and Taichi matched forward and decoded-gradient parity on the same 8192 splats, but training could still turn all white because near-camera projection produced enormous xyz/scale gradients and then NaN decoded tensors; the renderer binned no valid splats and returned finite white background. Always check decoded tensor finiteness and use a train-space near plane large enough to keep `fx / z` gradients sane.
- fast-mac v6 active scheduling needs a much tighter auto gate than "some empty tiles exist." In noisy local sweeps, ~15-29% active-tile sparse/layered cases were mixed or slower because active scheduling still pays fixed background/scheduling overhead; the clear active-friendly case was clustered overflow at ~5% active tiles. Treat uniform random as `microbench_uniform_random`, not a real-world default selector.
- fast-mac v7 hardware blending is not automatically the win. After fixing depth order, quad bounds, and backward math it matched a tiny dense reference, and at 4K/64K it beat v6 direct on clustered forward-only (`129.8 ms` vs `253.7 ms`), but uniform forward was slower (`149.6 ms` vs `31.3 ms`) and backward was catastrophic (`~20-21 s`). Until CPU/shared-buffer round trips and backward architecture are replaced, v7 is a profiling branch, not the training default.
- Two-stage "stage-1 world tokens → stage-2 AR novel-view generator" designs re-introduce the camera-leakage they were supposed to fix. Stage-1 tokens silently bake camera-specific info from the reconstruction loss, so stage 2 either expensively patches a broken representation or learns to ignore the tokens and runs as a standalone video model. Prefer one-stage splat-token + fixed differentiable rasterizer designs with multi-camera loss per step (GT camera photometric + perturbed camera diffusion-as-loss); view-independence is a property of the loss, not a second stage.
- Renderer speed and renderer train parity are separate claims, and tiny easy reference tests are not enough. fast-mac v5 looked forward-correct but failed the 32px/23-frame/512-splat train parity run (`~0.177` eval loss vs dense/Taichi `~0.066`) because saturated/crowded backward used per-pixel loop bounds around `threadgroup_barrier()`. The same barrier-control bug was present in v6/v6-upgrade. Barrier control must be tile-uniform; after looping over uniform `stop_count/count` and masking per pixel inside the loop, saturated gradients matched Taichi/reference and the same v5 control reached `~0.070` eval loss.
- After the v5 saturated-backward fix, 128px/4fps local training with `128 tokens * 512 splats/token = 65,536` splats is practical on MPS: no NaNs/OOM over 1000 steps, about `4.13 it/s`, W&B `3piy8cww`, full-video `Eval/Loss 0.10858`, `Eval/SSIM 0.49289`, `Eval/PSNR 18.93`. The final sampled train loss can land on a hard window and should not replace full-video eval.
- A 960-cell v6/v6-upgrade matrix weakened the idea that the chief-scientist upgrade should replace local v6 wholesale. Local v6 won 146/240 workload groups vs upgrade 94/240, but `v6_upgrade_direct` became competitive at 64k splats (median `-0.5%` vs `v6_direct`, 42/80 wins), especially forward+backward. Treat v6-upgrade as a source of mechanisms to ablate, not as the default renderer.
- The "working" bar for DynaWorld is structurally bounded, not aspirational: if the video backbone is frozen and the splat head is a cheap adapter, the ceiling of re-rendered novel views is the backbone's own reconstruction quality. This gives a falsifiable eval — same-camera round-trip should match `base_video_model(clip)` output; novel-camera re-render is adapter quality plus generative capacity on top. Do not pitch or evaluate against absolute photorealism; pitch and evaluate against backbone parity.
- Strategic architecture philosophy lives in `research_notes/meta_philosophy/` (north star, problem doc, mistakes log, prompt-guidance notes, LLM driver prompt), `research_notes/framing_the_problem/` (information-theoretic + contract + patched predictive-quotient framings), and `research_notes/training_contract_v1.md` (operational sampler/signature/loss/export contract). Do not mint `framing_4.md` for the predictive-quotient correction; patch framing 3 and use the training contract.
- Larger `frames_per_step` is mechanically viable with fast-mac v5 native batch rendering at 65k splats, but it is not a free quality win. `B=4/16/23/46` all fit; `B=4` was ~7.9 it/s but only ~31.6 frame-losses/s, while larger batches rose modestly to ~37-38 frame-losses/s; an equal-frame-budget `B=23,350-step` run (`yl8usu29`) underperformed the prior `B=8,1000-step` run on full-video eval (`Eval/Loss 0.1128` vs `0.1086`, `SSIM 0.473` vs `0.493`).
- Video-token implicit `recon_backward_strategy=batched` was a naming trap until it actually called `render_gaussian_frames`; after wiring that through fast-mac v5, the 128px/4fps 8192-splat implicit run learned cleanly in 100 steps (`z60o3ngd`, `Eval/L1 0.1034`, `Eval/Loss 0.1552`) but still trailed the 65k known-camera target (`Eval/L1 0.0723`, `Eval/Loss 0.1086`). Treat it as a working baseline, not yet a parity result.
- The video-token implicit single-frame-reuse bug was real and two-layered: the trainer normalized every sampled window to local `0..1` time, and the model injected time only after query-to-video attention. Preserving absolute sequence times plus injecting `time_proj` before query cross-attention made motion measurable (`gypzvibd`, 500 steps: temporal-to-first L1 ratio `0.458` vs `0.130` before), but adjacent motion is still far too smooth (`TemporalAdjacentL1Ratio 0.037`), so do not treat the implicit baseline as temporally solved.
- The bad 128px video-token implicit render was not a renderer regression: its Gaussian head still zero-initialized all 8192 splats to identical gray opacity-0.5 blobs at `xyz=0`, unlike the bounded-random 8192 known-camera init. Porting `GaussianParameterHeads` fixed the init contract, but 200-step probes stayed around `Eval/Loss ~0.149-0.150`; widening camera range improved accumulated temporal motion but not reconstruction. The remaining gap is baseline-contract/architecture, not just init.
- Image-implicit camera is not generically broken: a paired 32px/2fps/23-frame/512-splat 100-step rerun on the same sequence gave image-implicit `Eval/Loss 0.0603`, `SSIM 0.591` (`mv4ggjq8`) vs known-camera feed-in `Eval/Loss 0.0659`, `SSIM 0.513` (`w3a14cnp`). The 128px degeneration is specific to the video-token/full-scene contract, not the idea of learning cameras by photometric overfit.
- Wiring explicit normalized frame-index time into the video-token encoder, query decoder, and final head tokens did not solve the 128px implicit gap (`febn4gq6`, 200 steps: `Eval/Loss 0.1541`, `SSIM 0.272`, temporal adjacent ratio `0.017`). Time must be explicit for correctness, but the remaining failure is deeper than missing `t`.
- Raising video-token implicit capacity from 8192 to 65536 splats changed behavior more than quality: the 100-step 64k run (`2vllet1i`) stayed stable and unlocked much larger camera motion (`rot 7.19 deg`, `trans 0.604` vs `~1.02 deg`, `0.137` at 8192), but reconstruction improved only slightly (`SSIM 0.284` vs `0.272`). Capacity matters, but the remaining bottleneck is not just "too few splats."
- Fisheye ray generation can be forward-finite while autograd is broken at the principal point: `torch.where(r > eps, x / r, 0)` still evaluates the hidden `0/0` branch and can NaN gradients for focal/intrinsics. Clamp the radius before division/sqrt in differentiable camera math.
- A pure per-splat Metal VJP for pinhole `3D->2D` projection is the right v8 move. Replacing Torch-rematerialized projection backward cut warm MPS forward+backward from v5 `21.8ms` to v8 `11.1ms` at `128px/8192`, and from `41.2ms` to `22.3ms` at `256px/65536`; forward also improved at large count (`11.8ms` -> `5.8ms`). The main grad diff is camera-pose atomic accumulation (`~3e-2` abs on `~2e4` grad), while per-splat means/scales/quats stay near fp32 noise.
- The named v9 project3d-train fork preserves the same lesson with a clean namespace and benchmark path: staged fusion beats a literal mega-kernel. On warm MPS `--warmup 5 --iters 10`, v9 reduced `256px/65536` from v5 `16.63/39.26ms` forward/forward+backward to `5.92/17.32ms`, while keeping image max/mean error at `2.2e-5/2.2e-8`.
- Full `v5/v8/v9` project3d sweeps need all-case gradient checks and more than one timing row. With `--grad-check all`, v8/v9 matched v5 images at `~1e-7..1e-5` max error and per-splat gradients near fp32 noise, but MPS train means were noisy enough that v9 was not uniformly faster than v8 despite the cleaner namespace. Keep v8/v9 side by side until a median/p95 harness or fused next kernel settles the winner.
- PowerFoam power-face signs are a real footgun: the correct plane uses `+ r_i^2 - r_j^2` for cell `i` clipped by neighbor `j`. The first local Metal prototype and its CPU mirror both had the radius terms flipped, so mirrored reference tests alone would not catch the paper-equation error.
- Do not conflate direct GS fit init with token-GS init. `FreeDynamic3DGS` fit samples first-frame pixels for xyz/color, while the strong token-GS configs can intentionally use uniform RGB init; a random step-1 token video does not prove the direct GS fit baseline starts random. PowerFoam smoke should use image-seeded init when the comparison target is direct GS fit.
- Image-grid color seeding is not enough to make the toy PowerFoam renderer line up. Step-0 W&B logs still showed poor init (`16f/32 cells L1 ~0.206`, `1f/64 cells L1 ~0.256`), so the missing pieces are likely the official surface/texel/color-query model and adjacency, not just random RGB init.
- Full PowerFoam-style texel/plane/view-color attributes fix the local "blurry solid cells" issue at single-image scale: 128px/128-cell reference went from step-0 `L1 0.0720` to step-100 `L1 0.0369`, slightly ahead of the earlier direct GS single-image `L1 0.0382`. The video path needs param groups/Metal speed; single large LR destabilized 16-frame eval.
- PowerFoam camera-facing init has to rotate the official +x normal to `-z`, not `+z`. The wrong quaternion sign made the new normal loss penalize step 0 (`normal_loss ~0.82`); after flipping the sign, the 64px full tiny smoke initialized at `L1 0.0483` and step 2 reached `L1 0.0393` with `normal_loss 0`.
- The first trainable PowerFoam Metal path is a core bounded-cell renderer, not full paper PowerFoam. Its streaming replay backward matches Torch autograd to `~3e-6` on points/radii and trains 256 per-frame cells at 64px/16f from `L1 0.0547 -> 0.0362` in ~1.2s train-loop time, but visuals remain cell-like because oriented planes/detail-site/SV texture/densification are still absent.
- Adding Metal midpoint-linear cell texture is a cheap quality step but not the full fix: 1024 cells/64px/16f improved eval from constant `L1 0.03016` to linear `0.02786`, with only ~5-6% kernel total-median overhead at 128px/1024, yet previews remain cell-based. The next quality jump still needs the real oriented surface/detail-site/SV model.
- Fixed surface-linear Metal sampling is a quality win only after opacity calibration: `density_init=16` collapsed to stippled coverage (`L1 0.0790`), while `density_init=64` reached `L1 0.02378` at 1024 cells/64px/16f and beat midpoint-linear. The cost is real too: 128px/1024 fwd+bwd rose to ~23.96ms vs ~11.69ms for midpoint-linear, so learned surfaces need speed work before becoming the default.
- Learned Metal surface normals are correct and trainable but not the main missing piece on the tiny front-facing video: oriented-surface reached `L1 0.02367` vs fixed surface `0.02378`, with normal delta `~0.12` and similar `~22.5ms` fwd+bwd cost at 128px/1024. Expect the next meaningful quality jump from detail sites / SV color / densification, not normals alone.
- Learned local detail sites are the first meaningful Metal PowerFoam quality jump after surfaces: oriented texel-surface reached `L1 0.01899` on the 64px/16f/1024-cell smoke, with center/normal/texel-site drift all nonzero.
